# Task 3 Interview Defence Answers (`interview-answers.md`)

All 14 assessment questions plus the bonus account enumeration question, answered in under 200 words each.

---

### 1. Why is client-side validation not enough?
Client-side validation executes entirely inside the user's browser—an untrusted environment controlled by the user. Anyone can disable JavaScript, edit DOM attributes in Chrome DevTools, or skip the browser completely by sending raw HTTP requests via `curl`, Postman, or automated Python scripts straight to your API endpoint (`evidence/16-direct-request-command-and-response.txt`). Client-side checks exist solely to give fast, helpful UX feedback to cooperative humans; only server-side validation can protect database integrity and security.

### 2. What security checks belong in the frontend, and what must the server enforce regardless?
Strictly speaking, **zero true security enforcement belongs solely in the frontend**. The frontend should implement usability and input-hygiene safeguards: real-time format hints, character counters, `inputMode="numeric"` restrictions, disabling/dimming buttons to prevent accidental double-clicks, and masking password inputs (`type="password"`). Regardless of what the frontend checks, the **server must independently enforce** authentication, role-based authorisation, schema validation (types, lengths, regex patterns, allowed enums), rate limiting, CSRF protection, and parameterised database queries on every incoming request.

### 3. The user interface hides the delete button for non-administrators. Is that enough?
No, hiding a button in the UI is security through obscurity and provides zero actual protection. The underlying HTTP endpoint (e.g., `DELETE /api/users/:id`) still exists on the server. An attacker or curious regular user can inspect the frontend JavaScript bundle to discover the API route and send a direct `DELETE` request using `curl` or `fetch` with their ordinary session cookie. Unless the server middleware explicitly verifies that the authenticated user holds an `ADMIN` role (authorisation) before executing the deletion, any user can delete records.

### 4. What is the difference between validation, encoding and sanitisation?
* **Validation** checks whether incoming data conforms to an expected contract (type, length, format, range) and **rejects** the input if it fails (e.g., rejecting `"a@b"` because it lacks a top-level domain).
* **Sanitisation** modifies or strips unsafe/unwanted parts of the input to make it safe before storage or processing (e.g., `.trim()` stripping leading/trailing whitespace, or stripping `<script>` tags from rich text).
* **Encoding** transforms characters into a safe representation for a specific output context (e.g., converting `<` to `&lt;` in HTML to prevent XSS) without altering the underlying meaning.

### 5. Why should you validate route parameters and query strings, not just the body?
Route parameters (`/users/:id`) and query strings (`?mode=signup&page=2`) are just as attacker-controlled as a JSON request body. Attackers frequently tamper with URL parameters to attempt Insecure Direct Object Reference (IDOR) attacks, SQL/ORM filter injection, path traversal, or Denial of Service (e.g., passing `?limit=999999999` or `?page=-5` to crash database pagination). Every external input vector—body, query params, route params, and headers—must be validated against a strict schema at the server boundary.

### 6. Explain what a single page application is, and how you make one discoverable by search engines.
A Single Page Application (SPA) loads a single HTML shell and dynamically updates the DOM in the browser via JavaScript as the user navigates (`window.history.pushState`), avoiding full-page server reloads. Because pure client-rendered SPAs initially serve an empty `<div id="root"></div>`, search engine crawlers and social link previewers (like WhatsApp OpenGraph scrapers) may fail to index page content. To make an SPA discoverable, you use **Server-Side Rendering (SSR)** or **Static Site Generation (SSG)** (as Next.js App Router does), inject dynamic `<head>` metadata (`title`, `description`, `og:*`) per route, and maintain clean, crawlable URLs with a `sitemap.xml`.

### 7. What are the advantages and disadvantages of a single page application against a multi-page application?
* **Advantages of an SPA:** Instantaneous view transitions (`< 1ms`) with zero network round-trips (`evidence/04-form-switch-logs.txt`), preserved client-side state across views (e.g., carrying a typed email from Login to Reset Password automatically), and reduced server bandwidth for repeated navigation.
* **Disadvantages of an SPA:** Larger initial JavaScript bundle download (slower Time-to-Interactive on budget mobile devices), increased client memory consumption, complex manual accessibility management (announcing route changes and managing focus for screen readers), and potential browser history/`popstate` synchronization bugs compared to native Multi-Page Application (MPA) loads.

### 8. Can you explain the four principles of the Web Content Accessibility Guidelines, with examples from your own work?
WCAG is built on the **POUR** principles:
1. **Perceivable:** Information must be presentable in ways all senses can perceive. *Example:* We added a `⚠` caution icon and text beside every error (`src/app/auth/page.tsx`) so red-green colour-blind students do not rely on `--color-error` red borders alone.
2. **Operable:** All UI components must work via keyboard without a mouse. *Example:* We used `aria-disabled="true"` instead of `disabled` so keyboard users can `Tab` onto the submit button and press `Enter`.
3. **Understandable:** Content and operation must be predictable. *Example:* Real-time email hints on signup vs. on-submit checks on login.
4. **Robust:** Semantic markup (`aria-invalid`, `aria-describedby`, `role="alert"`) works reliably with assistive technologies like macOS VoiceOver.

### 9. Discuss the importance of semantic HTML in the context of accessibility.
Semantic HTML (`<main>`, `<header>`, `<nav>`, `<form>`, `<label htmlFor="...">`, `<button type="submit">`) gives browsers and screen readers built-in accessibility behaviour for free. A native `<button>` automatically receives keyboard focus (`tabIndex=0`), responds to both `Enter` and `Spacebar`, and announces its role as `"button"` in VoiceOver—whereas a `<div onClick={...}>` is invisible to keyboard navigation and screen readers unless manually patched with ARIA attributes and keydown listeners. In our audit (`docs/accessibility-audit.md`), moving our disabled-click handler from a non-semantic `<div>` onto the semantic `<button>` immediately restored keyboard operability.

### 10. Tell me about a time when you disagreed with what a customer wanted to build.
While designing an admissions portal workflow, a stakeholder wanted to collect 12 fields upfront on the initial registration screen—including guardian phone numbers, residential street addresses, and a mandatory 6-digit number input with a placeholder reading `"Enter 6-digit PIN"`. I disagreed because excessive upfront fields hurt mobile conversion on 3G networks, `<input type="number">` introduces leading-zero corruption (`0400`), and leaking the PIN length in the placeholder reduces an attacker's brute-force keyspace. I proposed collapsing the form to essential onboarding fields, using `<input type="text" inputMode="numeric">`, and omitting the shape-leaking placeholder, which protected security while keeping completion fast.

### 11. How would you explain to a non-technical executive why their AI implementation is not performing as expected?
I would avoid jargon like "context window" or "hallucination" and use an operational analogy: *"Think of the AI agent like a fast, newly hired contractor who hasn't been given your company handbook or quality checklists. Right now, it is guessing what 'good' looks like, which is why the interface looks complete on screen while failing silently behind the scenes. To fix performance, we need to give it strict boundary rules (design tokens and database schemas), break tasks into small verified steps rather than asking it to build the whole product at once, and put deterministic server guardrails around its output."*

### 12. One of your validation rules wrongly blocks a category of legitimate user. Name the rule, name the users, and defend the trade-off or say you got it wrong.
Our **Legal Full Name rule** (`src/app/auth/page.tsx`, Lines 65–67) requires at least two space-separated words where each word is at least 2 characters long (`cleanName.split(" ").length < 2 || cleanName.split(" ").some(w => w.length < 2)`). This rule **wrongly blocks legitimate mononymous users** (people who legally have only a single name on their government ID) as well as applicants who use a single-letter initial for their first or middle name (e.g., `"J. Adeyemi"` or `"Olu A"`). We knowingly defend this trade-off on our self-serve web form because single-token bot spam (`"a"`, `"test"`) is our highest-volume automated attack vector, and the few mononymous students enrolling at our physical Ibadan campus can be registered via manual registrar override at the bursary desk.

### 13. You sent a request directly to your own endpoint. Say exactly what happened and what it tells you about the eight rules you spent two days writing.
When we ran `curl -i -X POST http://localhost:3000/api/enquiries` with `{"fullName":"a","email":"a@b","track":"Bypassed-Via-Curl-Attack"}` (`evidence/16-direct-request-command-and-response.txt`), our server immediately returned **`HTTP/1.1 201 Created`** and wrote that corrupted row straight into PostgreSQL. It enforced **zero out of eight** client-side rules we spent two days building. This proves that our eight frontend rules are purely a UX convenience for honest users typing in a browser; to an attacker who skips the browser, client-side validation might as well not exist until every single rule is duplicated on the server in Task 4.

### 14. Wrong-answer analysis: "I use strong client-side validation with regex on every field, disable the submit button until everything is valid, and sanitise all inputs in the browser before sending them. That covers the main injection and bad-data risks."
* **What is useless for security:** Disabling the submit button, running browser regexes, and sanitising inputs in the browser are completely useless against injection or bad-data attacks because an attacker sends payloads straight to the server endpoint via `curl`, bypassing the browser entirely.
* **What is actively misleading (and harmful to accessibility):** Claiming this "covers the main injection risks" creates a false sense of security that leaves the backend defenceless, while using a native `disabled` submit button breaks keyboard tab order for screen-reader users (`docs/accessibility-audit.md`).
* **What the candidate confused:** They confused **client-side UX input assistance** with **server-side security boundary validation and output encoding/parameterised queries**.

### Bonus Question: What is user enumeration, and how do error messages contribute to it?
**User (or account) enumeration** is a vulnerability where an attacker can systematically probe an application's login, registration, or password-reset endpoints to determine which email addresses, usernames, or PINs actually exist in the database. Error messages are the primary vector: if a login form returns `"Email address not found"` for an unknown email but returns `"Incorrect password"` for a registered email (or if a password-reset screen says `"No student record matches that email"`), the application acts as an oracle. An attacker can feed a list of 50,000 Nigerian email addresses into the endpoint, harvest every confirmed student email, and launch targeted credential-stuffing or phishing attacks against those verified accounts—which is why authentication errors must always return a generic `"Incorrect email or password"`.
