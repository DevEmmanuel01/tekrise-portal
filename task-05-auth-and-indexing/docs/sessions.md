## 1. Why We Chose Stateful Server-Side Sessions Over Stateless JWTs
For the Tekrise Academy Student & Admissions Portal, we implemented **stateful server-side database sessions** (`public."Session"`) rather than stateless JSON Web Tokens (JWTs) for three security reasons:
1. **Immediate Server-Side Revocation:** A stateless JWT remains valid until its `exp` timestamp expires because the server stores no state. If a student signs in on a shared laboratory computer at the Ring Road Ibadan campus (or loses their phone) and later resets their password, a stateless JWT cannot be revoked without building a server-side blocklist (which reintroduces database state anyway). With our `Session` table, deleting the row (`DELETE FROM "Session" WHERE id = $1`) revokes access across the entire portal on the very next request.
2. **Zero Payload Exposure in the Browser:** JWT payloads are only Base64Url-encoded, meaning anyone inspecting client storage can read the embedded user ID, email, and role claims. Our opaque 32-byte random hex token (`crypto.randomBytes(32)`) contains zero sensitive claims.
3. **Live Role & Account-State Enforcement:** Every authenticated request joins `Session` to `Student` (`getAuthenticatedStudent` in `src/lib/session.ts`), ensuring that role changes or account suspensions take effect immediately rather than waiting for a token refresh cycle.

## 2. Why We Store `SHA-256(rawToken)` in `Session.tokenHash` Instead of the Raw Token
When `createServerSession()` generates a 32-byte (64-hex-character) token via `crypto.randomBytes(32)`, it sends the raw token to the browser cookie (`01-session-cookie-devtools.png`) but stores only `crypto.createHash("sha256").update(rawToken).digest("hex")` in `Session.tokenHash` (`02-session-row-db.png`).
* **Why Hash Session Tokens at Rest:** If an attacker obtains read-only access to our PostgreSQL database (via a compromised backup, SQL injection in a reporting tool, or leaked read-replica credentials) and raw session tokens are stored in plaintext, the attacker can copy any active `token` into their browser cookie and immediately hijack student and `REGISTRAR_ADMIN` accounts. Because SHA-256 is one-way, a leaked `tokenHash` cannot be reversed into the valid `tekrise_session` cookie value.
* **Why Fast `SHA-256` Is Safe for Session Tokens (Unlike Passwords):** In Task 4 (`docs/hashing.md`), we proved why fast `SHA-256` is catastrophic for human-chosen passwords (which have low entropy and are vulnerable to dictionary guessing). However, a session token generated by `crypto.randomBytes(32)` has **$2^{256}$ bits of cryptographic entropy** ($1.15 \times 10^{77}$ possibilities). Because no attacker in the universe can brute-force a 256-bit random keyspace, memory-hard Argon2id is unnecessary on every HTTP request; a single `SHA-256` hash (`~0.00045 ms`) provides full preimage resistance with zero per-request latency overhead.

## 3. Cookie Flag Specification & Threat Mitigation (`buildSessionCookieHeader`)
Every `tekrise_session` cookie is issued with the following security attributes:
1. **`HttpOnly`:** Prohibits client-side JavaScript (`document.cookie`) from reading or modifying the session cookie. If an attacker ever discovers a Cross-Site Scripting (XSS) vulnerability on a page, injected scripts cannot exfiltrate the `tekrise_session` token to an external server.
2. **`SameSite=Lax`:** Prevents the browser from attaching the `tekrise_session` cookie on cross-site `POST`, `PUT`, or `DELETE` requests initiated from third-party domains (defending against Cross-Site Request Forgery / CSRF attacks), while still allowing the cookie to be sent when a student clicks a top-level `GET` navigation link from their email verification message back into the portal.
3. **`Secure` (Enforced in Production HTTPS):** Instructs the browser never to transmit the cookie over unencrypted plaintext `http://` connections, preventing Wi-Fi packet sniffing on campus networks. (Omitted only on `http://localhost:3000` during local development so Chrome accepts the cookie without TLS).
4. **`Path=/` & `Max-Age=604800` (7 Days):** Scopes the session across all portal API routes and enforces a 7-day hard expiration matching `Session.expiresAt` in PostgreSQL.
